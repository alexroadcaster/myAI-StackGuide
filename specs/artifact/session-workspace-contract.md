# Session Workspace Contract

CP-03 addendum for R02-R05, R07, R10-R15. The owner-approved [desktop design](../../docs/plan/plugin-v1-session-workspace-design.md) supplies the subsection inventory. This document supplies canonical joins, compatibility and semantic validation requirements. Schemas and examples are contract evidence; no writer, renderer, translation model, browser workflow or migration is implemented here.

## Canonical Sources And Versions

`state.json` remains the only current domain store. New writes require state `schema_version=1.1.0`, `content_revision`, `presentation` and `scan` (nullable). Its intake and non-null Brief/memo/integration plan use `1.1.0`; C2/C4/C9 source/index/query/card/pack contracts remain `1.0.0`. Corrections may retain legacy `1.0.0` events; new `context_details` corrections require `1.1.0` and the existing Brief-bump/invalidation rule. Contract-family `$id` URLs retain `/v1/`; each schema explicitly dispatches the supported minor version.

Affected schemas also accept their original `1.0.0` shape for read-only validation. New properties are forbidden in that legacy branch. This does not authorize editing old state, rewriting finalized history or assuming that old consumers understand the additions. CP-07 must reject incompatible write/resume attempts visibly. A future explicitly requested migration/new run must retain the old bytes and identify the predecessor; no migration is delivered here. A compatible reader can render a legacy run with missing-localization/structured-detail notices and the documented `ru` default, without saving an upgrade.

The current state stores the existing bounded C2 `scan-report` as `scan`, including safe file dispositions and measured counters; it can exist before a Brief. `scan=null` means no retained scan result, not zero files. When constructing the Brief, its observed facts/evidence retain the scan source; subsequent interpretation corrections do not rewrite that scan. There is no raw-chat/source archive. Duplicate scan/Brief evidence with the same ID must identify the same source; contradictory duplicates are rejected.

`brief.details` adds sourced problem, target user, workflow, current/target behavior, baseline, scope/non-goals, constraint notes and tensions. A claim has `text`, `kind`, `evidence_refs`, `answer_ids`, and `limitation`. Unknown claims have null text, no invented refs and an explicit limitation. Observed claims need project/public evidence appropriate to their owning object; user statements need saved-answer provenance; inferences remain interpretations. Answer IDs resolve to answered, sanitized intake records, not skipped/null answers. A baseline claim is a recorded statement/observation, never a fabricated measurement. `brief.success_criterion` is a target until a later execution-evidence contract exists.

`intake.questions` is the bounded canonical question ledger, joined to answers by `question_id` and ordinal. It records question text, rationale, consequence, examples and topics, without chat turns. IDs and ordinals are unique and contiguous; every answer/pending question joins exactly once, and no extra question is invented. `ready` requires `completion_reason`; zero-question asking is valid before the first question, and zero-question ready still requires sufficient explicit reviewed context. The ten-question ceiling remains unchanged.

`memo.comparison_details`, `memo.avoid_defer_details`, and `integration_plan.details` provide the structured comparison, revisit conditions, proposed graph, prerequisite checks and first validation. They supplement retained prose, never contradict it or create a second recommendation. Missing rows remain unknown; no-change is explicitly a baseline, not an invented retrieved card. `step_dependencies` joins every existing step exactly once to earlier step IDs and source-supported safe relative paths. It cannot execute displayed commands.

## Localization Binding And Validation

`localized-presentation.schema.json` is embedded only at `/presentation`. It stores a default `ru|en`, original source-language metadata (`und` is permitted when genuinely unknown), a presentation revision, current content revision, nullable current Brief/memo/plan identities, bounded entries and per-locale coverage. Per-field source locale supports mixed-language sanitized input. Language metadata is not evidence that a translation is accurate.

Each entry contains `field_pointer`, `source_sha256`, `source_content_revision`, `source_locale`, derived `evidence_refs`, derived `canonical_literals`, and `ru`/`en` objects `{status: available|missing, text: string|null}`. Pointers are allowlisted narrative leaves only, never arbitrary JSON, filesystem paths, source quotations, technical identifiers, commands or presentation fields. A resolver validates the state before resolving array indexes; no pointer can follow an external reference. Example: `/intake/questions/0/rationale` or `/memo/recommendations/0/fit_rationale`.

The source digest is `sha256(json.dumps(resolved_string, ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False).encode('utf-8'))`. Compare it to the actual canonical source, not to another string supplied by the translation. Bind run ID, content revision, Brief identity/version, memo ID and plan ID to state, including null identity before those objects exist. Reject stale same-ID translations if source bytes changed.

Enumerate all non-null string leaves matching the schema's `fieldPointer` allowlist. `required_fields` is the size of that canonical set. An entry may occur at most once, must resolve to that set, and counts as available only if its source/hash/identity checks pass and the selected locale has available text. `available_fields` is recomputed per locale. `complete` means every required field is available; otherwise status is `partial`. Up to 512 entries fit the presentation budget; omitted entries are missing translations, not invisible source content. A zero-field early state has complete coverage with zero counts. For source locale `ru` or `en`, an available source-language text equals the canonical string exactly.

Evidence is also a join, not translation-authored provenance. For a field, derive refs from its nearest owning record's `evidence_refs` or `evidence_ref`; fact/inference fields resolve their fact basis; linked claim `answer_ids` are canonical saved-answer provenance; fields without explicit refs use an empty list. The order is canonical sorted unique. All refs must resolve to the run's minimized project evidence or packed public card evidence. Translations cannot add or remove references to change a claim's support. `evidence_refs` is not permission to copy source text.

Derive `canonical_literals` from the resolved source text using known canonical repository/product/full-name, ID, URL, safe path, command and technology values already present in typed source fields, plus explicitly delimited inline literals. For alphanumeric edges of technology/name/ID values, require case-sensitive Unicode-aware word boundaries; `Go` in `Goal` and `C` in `Compare` are not literal occurrences. This is bounded matching, not natural-language inference. Preserve explicit inline literals as atomic values (`C++` does not introduce a nested `C` literal), plus exact URL/path/command values. Use sorted unique exact strings, and compare the entry list to that derivation. Both available languages must retain every derived literal exactly. A translator-declared empty list cannot bypass this comparison. Literal detection cannot establish full semantic equivalence: the C8 human rubric additionally checks named technology terms, negation, uncertainty, scope, role, hard constraints, execution state and authority. Do not claim schema validation proves translation quality.

Missing target text renders the original canonical string with its actual source `lang` and a translation-unavailable notice. Original sanitized user statements remain accessible with provenance even when a translated view is available. Raw source/source quotations are not persisted by these contracts; technical source references are shown unchanged. Static dictionary gaps fail CP-10's build; runtime missing prose yields partial presentation without API/model retries. Fragment locale -> saved default -> documented `ru` is the selection order. Browser language/view/compare changes never mutate state, retrieval, model inputs or selected candidate identities. No localStorage, fetch or service is required; no-JS retains the useful saved-default report with an honest switch-unavailable notice.

## Revision Domains, Size And Immutable History

`revision` counts successful state commits. `content_revision` starts at 1 and advances for a domain change, including intake, scan, Brief, request/result/memo, correction and finalization. A saved default-locale-only or translation-only change advances storage revision without changing content revision, Brief version, query, pack or memo. `presentation_revision` advances when its entries/coverage/source bindings change; default-locale-only changes do not advance it. Browser preferences advance none of these.

On a domain change, rebind presentation to the new content revision; unchanged field bytes can retain their translation without a model call. Changed fields require new validated text or become explicit missing/omitted entries with original fallback. Never retain a stale hash as available. A semantic Brief correction increments Brief version and invalidates downstream results under the existing contract; changing audience/workflow/scenario/scope through `context_details` uses the same rule. Do not treat a render retry as a new composition.

Finalization commits the complete final state, including its final presentation and revision bindings, before creating identical immutable run bytes. Translation added later cannot modify that finalized current state or history. A future user-requested derived/new-run workflow must identify its source/predecessor and use the accepted writer; this addendum does not implement an alternate persisted derived-view format. Read-only fallback rendering of a finalized run needs no mutation.

Existing ceilings stay fixed: state 2 MiB, HTML 5 MiB, public evidence pack 48 KiB, total model input 88 KiB, Brief 16 KiB, integration plan 48 KiB, memo 128 KiB. Presentation adds a 512 KiB sub-limit inside the state ceiling; scan retains its existing 256 KiB sub-limit. The state/scan/presentation are not wholesale model inputs. Narrative translations are outputs, not duplicated public evidence or extra retrieval inputs. CP-04/11 measure added composition cost/latency and size separately. Every byte annotation uses compact UTF-8 JSON measurement and requires semantic/runtime enforcement; the standard JSON Schema validator alone does not enforce annotations. On limit failure preserve current saved data and report partial presentation/error; never drop canonical evidence, silently enlarge limits, prune history or create retry debris.

## Commit And Publication Outcome

`publication-result.schema.json` defines a transient operation response to Codex, not another file or a field saved in finalized state. CP-07 owns the single writer/orchestrator; CP-10 supplies rendering. The same boundary serves session creation, saved answers/phases, corrections and finalization. HTML remains `docs/myai-stackguide/status.html`.

`saved` identifies the successfully committed target of this operation, or the already validated target of `render_only`. `current` is the current run/revision/content revision observed under lock before reporting/publication. `published` identifies verified bytes actually at the HTML path, including run/revision/content revision, presentation revision, generation timestamp and SHA-256; it may be a preceding run. Null means no validated HTML exists, not a made-up zero revision. All stamps require `content_revision <= revision`.

| Outcome | Required meaning |
| --- | --- |
| saved + current | Successful commit and render; saved/current/published run/revision/content revision match, and the presentation revision/hash refer to actual rendered bytes. |
| saved + unavailable | First publication failed; saved answers persist, published is null, Codex says no HTML is available yet. |
| saved + stale | Rendering/replacement failed; published retains the older valid HTML run/revision and differs from current, saved state is preserved. |
| saved + superseded | A newer run/revision won before replacement. Captured saved target differs from current; the late render is never published. Existing published bytes are preserved. |
| not_saved + not_attempted | Commit failed; saved is null, render_attempts=0, publication is not attempted and no answer is described as saved. |
| render_only + not_attempted commit | Re-render validated saved state without answers, scan, retrieval, translation or model replay; no domain mutation. |

At most two render attempts occur in an operation: initial rendering plus one retry for `render_failed` or `html_write_failed`, only while the same captured state is current. At two attempts retry is stop/none. Busy/conflict/integrity/storage/version failures stop; no hidden loop restarts. A different current target needs a distinct explicitly requested render-only operation. Automatic orchestration of the initial commit plus bounded render retry remains the normal path, not a second manual command after every answer.

After rendering, reacquire the existing OS lock and compare run/revision/content revision before replacement. Reject a late render as `render_superseded`. A successful publication must match actual bytes and current state; self-declared receipt values are insufficient. For stale/superseded outcomes, retain the last validated published receipt if available. Render preparation does not hold the lock across model/scan/user waits.

The retained state `html_revision` has precise compatibility semantics: in 1.1.0 it is null or the prior same-run publication known at commit time, strictly less than the new revision. It is not a promise about the render following that commit. A new run resets it to null even if predecessor HTML exists. The authoritative result of that render is the transient publication outcome and HTML's generation metadata. Never commit state again just to update `html_revision`, especially after finalization. Existing 1.0.0 values retain their old read-only interpretation.

Opened standalone HTML knows only its own generation revision/time, explicitly in UTC (`Z`), or another timezone supplied by a future validated renderer input; it never guesses timezone from RU/EN. Codex reports publication failure outside an old file, links the same HTML after success, and asks the user to reload when needed. An old file cannot inspect newer state, failed commits, storage usage or writer locks. History/recovery panels show only operation evidence actually available at generation.

## Verification Ownership And Remaining Gates

Quality Evaluator owns positive/negative fixtures and semantic checks. Required cases include early no-goal/current-question/manual states, known and unknown scenario claims, saved answer/question joins, scan-before-Brief, comparison baseline/unknown/hard exclusion, sourced graph/prerequisites/step dependencies, RU/EN partial coverage and forged complete counts, stale source digest at unchanged Brief ID, changed technical literal, unresolved evidence/answer, default-locale-only transition, semantic correction invalidation, finalized-state mutation, first-render failure, saved/published mismatch, competing newer revision and bounded render-only retries.

Draft 2020-12 covers structure, enums, version branches, allowlisted pointer shape, limits on items/text, strict objects and selected status conditions. Cross-field identity, pointer resolution, computed coverage/digests/bytes, evidence/literal joins, semantic equivalence, actual commit/HTML bytes, lock behavior, immutable-history transitions and browser side effects require independent semantic/runtime checks. CP-04 owns C8 compatibility and quality rubric; CP-07/10/11 implement/verify runtime and CP-15/16 retain rendered/packaging acceptance. No static contract promotes those gates.

Rollback is a scoped reversal of this addendum's schema/doc changes against the saved starting bytes; preserve existing fixtures/history and unrelated work. No Git reset, artifact deletion, migration or permission change is part of rollback.
