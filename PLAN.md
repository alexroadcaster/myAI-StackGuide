### Accepted RepositoryCardV2 Decision

- `RepositoryCardV2` (`schema_version: 2.0.0`) is the only active public-card shape. Public card facts may not be split between the card and `data/plugin_catalog_metadata.json`; that sidecar is removed from CP-06 output scope. Historical v1 fixtures remain dated evidence only and are not an accepted runtime fallback.
- Canonical dedupe and join identity is the positive integer `identity.github_repository_id` across cards, index rows, retrieval results, evidence packs, recommendation memos and integration plans. `identity.catalog_record_id` and `identity.merged_catalog_record_ids` preserve exact frozen catalog lineage inside the card only; `identity.full_name_aliases` contains historical `owner/name` aliases only.
- Every card uses the same required sections: `identity`, `catalog`, `descriptions`, `classifications`, `repository`, `delivery`, `activity`, `advisory`, `provenance`, `evidence` and `corpus_kind`. Unknown scalar facts are `null`; unknown collections are `[]`. No display fallback mutates source metadata.
- `descriptions.upstream`, `descriptions.catalog` and `descriptions.catalog_origin` remain distinct. `classifications[]` is the only assignment representation and records category ID/title/kind/parent, `primary|secondary` role and direct-placement source. Containers remain pinned taxonomy nodes, not direct card assignments.
- `repository` owns languages, structured license/Stack, topics, repository flags and popularity signals. `delivery` owns one normalized form/deployment/hosting shape plus server, difficulty, lifecycle, maturity and persona facts. `activity` keeps creation, repository update, push, verified commit/release, sync and observation times distinct and normalizes legacy/CAT-07A observations into one typed array.
- `catalog` owns exact `accepted|candidate|reference|benchmark` status, status source, membership cohort, review status and evidence stage. `advisory` separately owns recommendation text, eligibility, adoption fields and explicit gaps. `provenance` and `evidence` remain public, bounded and field-addressable inside the card; request-specific recommendation role is not catalog status.
- FTS v2 is a derived, hashed projection rather than a second card model. Its explicit columns and initial uncalibrated weights are `full_name=5`, `full_name_aliases=5`, `upstream_description=3`, `catalog_description=3`, `topics=3`, `category_labels=1`, `use_cases=3`, `integration_surface=3` and `best_for=2`. CP-04 calibrates relevance; acceptance of these starting weights is not a quality claim.
- The active checked-in artifact set is now paired: card schema `2.0.0`, activity schema `2.0.0`, retrieval policy `2.0.0`, index format `2`, compatible query/result/evidence-pack/manifest schemas and matching fixtures. Historical v1 schemas remain resolvable only for non-C9 compatibility evidence; they are not an active card/index runtime fallback. Every future v2 consumer rejects mixed v1/v2 pins; there is no silent coercion, automatic rebuild, full-catalog prompt fallback or dual-version runtime.

## Verification Strategy

- Static control-plane validation before assigning agents.
- JSON/YAML schema validation and positive/negative fixtures before contract acceptance.
- Generated-output parity after any source or builder change.
- Recommendation evals with deterministic contract checks and human judgment before promotion.
- Runtime, browser, privacy, and GitHub permission evidence are later gates; static files do not prove them.

## Rollback

- Preserve all pre-existing dirty-worktree changes.
- Review the exact diff before reverting any artifact.
- Roll back only files created or lines added by the rejected slice; do not regenerate or overwrite unrelated catalog outputs.
- MCP, hooks, automation, workflows, deployment, Git history, and external systems remain unchanged, so no runtime rollback is required for `CP-S1`.

## Handoff Rule

Every agent receives a completed `.codex/artifact-templates/agent-task-packet.md` containing the task ID, complete context, allowed sources, owned and forbidden files, commands, expected evidence, stop conditions, and sequential fallback. Agents must return files touched, commands run, observed evidence, unsupported claims, risks, and the next role.
