# Research GitHub Candidates

## Workflow

1. Start from a bounded category, task archetype, Project Context Brief, or comparison question.
2. Search current GitHub and authoritative project sources within the task's public-research authorization. For the product discovery flow, honor its 3-5 sanitized-query and 20-candidate caps; do not send private context. Broader research needs its own bounded brief.
3. Record query, retrieval date, repository URL, source type, license and metadata status, evidence, caveats, and verification state.
4. Read Candidate Identity And Lifecycle in [Team contracts](../../../docs/plan/plugin-v1-team-contracts.md). Keep catalog status, evidence stage, and recommendation eligibility separate. Historical labels such as `normalized_candidate` are not automatic acceptance mappings. Preserve current catalog identity and dated live evidence separately.
5. Treat stars, forks, and freshness as triage signals, not endorsement or production-readiness proof.
6. Return source-grounded findings; do not edit canonical catalog data or generators.

## Output

Return candidate records, query ledger, duplicate notes, category proposal, evidence gaps, confidence, risks, and curator handoff.

## Stop Conditions

Stop on missing provenance, consequential stale claims, private-data need, unapproved authentication, external writes, or pressure to promote an unreviewed candidate.
